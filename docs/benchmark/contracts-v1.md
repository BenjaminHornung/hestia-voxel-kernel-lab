# Benchmark Contracts v1

BR01 owns renderer-, DOM-, Playwright-, worker-, telemetry-, and runtime-neutral contracts only. The productive base is `c64aeef1f51dd0ed2d8431411cf3ba1e84195b9d`; the governing C08 contract and prompts are bound to `377979a27f5ca8482a3bf534b9307653417b43bd`, and compatible source-pack detail is bound to `8b7582b209c1618a2974d1ec6849b6aace827a1f` (specification blob `6afb4e9b9de8e292b21fe462f523915c89e2d345`). These commit/blob references are provenance only; source-pack documents are not copied into product output. The older d959 research basis and pre-C08 claims are superseded.

The canonical hierarchy is `HardwareCellV1 -> BrowserProcessV1 -> BenchmarkRunV1 -> BenchmarkIterationV1 -> BenchmarkRawSampleV1`. Every variable environment/profile value uses the one shared `AvailabilityV1<T>` union; unavailable H1/H2/H3 evidence is represented as `value:null` with a reason and never reconstructed. Declared values are configuration, not runtime evidence. An eligible run requires observed environment/profile evidence, valid phase/runtime/capability state, and the non-headless/profile gate rule; otherwise eligibility is false and the run records a machine-readable reason. Unknown visibility/focus evidence remains structurally valid and is not compared with execution page state. The canonical display contract is 1920×1080 CSS pixels, DPR 1, 60 Hz, headed/visible/focused; these are workload bindings, not performance limits.

Scenario definitions are contract-only and stable-digest bound. The seven IDs are mesh-golden-world-v1, mesh-density-sweep-v1, scheduler-steady-v1, scheduler-burst-v1, brush-stress-v1, navigation-leak-v1, and backend-fixture-v1. BR01 does not execute scenarios or implement BR02 capture/mapping. Concrete H2/H3 device bindings remain owner decisions; structurally representable unbound profiles are not performance-eligible.

Metrics use the frozen BR04 union plus every canonical right-hand crosswalk reference. Scenario contracts store canonical `metricRef` values directly; historical names remain in the explicit crosswalk only and are not public metric fields. Memory requirements use `memory.bytes@1` with explicit `memory-kind` dimensions, including `js-heap`, `embedder-heap`, and `backing-storage` where required; the backend fixture's source does not bind a concrete kind, so its dimension remains explicitly `owner-bound`. Definitions are explicit, including unit/kind/domain, phases/containers, capability requirements, source-literal grouping and pairing, direction, effect/null, and `automaticDecision: forbidden`. The registry assigns one disposition to each BR02 record globally; `browser.long-task` and `scheduler.queue-depth` are emitted only by their matching metrics. Long-task count and any crosswalk without a frozen future producer remain diagnostic-only; the new `BR02`/`WP05`/`BR05` emit-sample mappings are stable future contracts but provide no current runtime evidence and do not make a run eligible until the matching producer emits a valid sample. The accepted BR04 sources provide explicit suffixes for chunk, scheduler operation, input/revision, memory kind, GPU, burst, counter window, and time block; other crosswalks retain unavailable grouping/pairing fields. Digest and liveness references are assertions, not performance gates. The neutral population floors are separate: 3 technical bootstrap processes, 5 standard-cell processes, 30 warm-measurement iterations, and 10 cold processes. Eligible warm measurement additionally requires independently accepted BR03 warmup minimum and stable evidence for the same process and plan. The supported trace artifact tuple is `traces/**/trace.json.gz` with `application/gzip` and `binary-exact`; `heap-snapshot` and `gpu-capture` remain fail-closed/unavailable pending evidence-backed standardization. BR01 receipt closure invokes an injected accepted BR02 adapter callback and binds only the actual telemetry bytes, complete ordered adapter results, target-run raw-sample projection, and their deterministic digests; it provides integrity binding, not adapter source-code or code-execution attestation. Bundle manifests bind one raw run, one telemetry export, and one validation receipt per logical run and sort run entries by `runId`; omitted, duplicate, foreign, unrelated, or reversed closure artifacts reject.
Warmup stability uses the BR03 median rule with the denominator `max(abs(previousMedian), abs(currentMedian), metricEpsilon)`. The fixed epsilon is owned by the metric (`0.001` for the three millisecond controls and `1` for scheduler queue depth); supplied warmups must stop at the first second consecutive stable comparison. Metric dimensions use an explicit key-to-domain owner map and fail closed for unknown keys or domains.

The frozen `BENCHMARK_METRIC_REACHABILITY_MATRIX_V1` contains 268 scenario/phase/backend/metric cells. Each cell names the future producer owner, record name, first work package able to emit it, capability-selected condition where applicable, and its fail-closed eligibility state before and after a valid producer record. `not-required-in-phase` cells are explicit; BR01 does not claim that a future producer exists today. The matrix is exported with the browser-safe metric registry and is included in the registry digest.

An `emit-sample` mapping in this registry is a frozen future producer contract, not current runtime evidence or an execution authorization. `diagnostic-only`, `context-only`, and control/invalidation records never satisfy a required metric; BR01 does not implement the named producers.
